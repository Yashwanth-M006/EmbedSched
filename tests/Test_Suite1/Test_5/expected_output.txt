[CRITICAL] [STATIC] stack_bss_zero_gap
  ────────────────────────────────────────────────────────────────────
  __bss_end__   = 0x20009D78
  __stack_start = 0x20009D78
  Gap between end of .bss and start of .stack section = 0 bytes

  The .stack section is placed IMMEDIATELY after .bss with no gap.
  If ANY new global variable is added to the firmware (increasing .bss),
  the linker CANNOT place the .stack section without overlapping .bss
  or overflowing SRAM1. There is zero growth margin.

  At runtime: the hardware SP starts at _estack (0x2001C000) and grows
  DOWN freely — the hardware does not enforce the declared .stack section
  boundary without MPU configuration. Stack growth below __stack_start
  silently corrupts the end of .bss (g_log_buffer, g_event_ring).

  Required message elements:
    1. Show __bss_end__ and __stack_start are identical addresses
    2. State gap = 0 bytes
    3. Name the specific .bss symbols at risk of corruption
       (those immediately before __bss_end__: g_proc_flags, g_sensor_cal)
    4. State that MPU guard is not configured (no guard region in LD)
    5. Suggest fix: increase _Min_Stack_Size OR move stack to CCM

  What this tests in the analyzer:
    - map_parser.py: extracting __bss_end__ and __stack_start symbols

    - gap == 0 → CRITICAL (not just WARNING)

This is the computation your analyzer must perform:

  Step 1 — parse buggy.ld:
    _Min_Stack_Size = 0x200  (512 bytes)

  Step 2 — parse firmware.map:
    __bss_start__ = 0x20000014
    __bss_end__   = 0x20009D78
    __stack_start = 0x20009D78  ← same address
    __stack_end   = 0x20009F78  (= __stack_start + 0x200)
    _estack       = 0x2001C000  (SRAM1 top)

  Step 3 — compute gap:
    gap = __stack_start - __bss_end__
        = 0x20009D78 - 0x20009D78
        = 0 bytes  → CRITICAL

  Step 4 — compute depth ratio:
    worst_depth = max over all call chains from .su + call graph
                = 256B (TIM3→isr_log→pack_record)
    ratio = 256 / 512 = 50.0%
    headroom = 256B
    → WARNING (not CRITICAL alone — depth is bounded and < budget)

  Step 5 — compute SRAM1 remaining:
    __heap_end   = 0x2000A178
    SRAM1 top    = 0x2001C000
    Free after heap = 0x2001C000 - 0x2000A178 = 73,352 bytes
    This space is the REAL runtime stack range — 143× larger than
    the declared .stack section. The declared section is misleadingly
    small relative to where the SP actually travels.

  Step 6 — BSS symbols at overflow boundary:
    The last symbols before __bss_end__ (at 0x20009D78):
    These are whichever symbols GCC places last in .bss.
    The analyzer should name them from the .map file to make
    the corruption warning concrete and actionable.
